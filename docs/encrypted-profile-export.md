# Encrypted profile export and account erasure (#454)

Deploy `20261119190000_privacy_jobs` through normal Prisma migrations, regenerate the Prisma client and run backend checks. Keep the existing pg-boss worker enabled: it processes privacy requests each minute and cleans expired cloud objects every 15 minutes. The PostgreSQL queue claims work with SKIP LOCKED, retries failed operations up to five attempts, and recovers stale running jobs after ten minutes. Per-user advisory locks serialize export and erasure; a failed operation is not reported as complete.

Configure `PRIVACY_EXPORT_BUCKET`, `AWS_REGION`, and the standard AWS credential provider chain. The bucket must be private with public access blocked, HTTPS required, tightly scoped PutObject/GetObject/DeleteObject permissions, and an expiration rule for abandoned exports. Prefer a dedicated non-versioned bucket; if versioning/backups are enabled, separately expire old versions and backups, because DeleteObject alone does not remove them. Uploaded objects are recipient-encrypted first and also request S3 SSE-AES256. Temporary AWS credentials can make signed links expire earlier than the requested lifetime.

Under both API aliases, authenticated users with PROFILE_UPDATE_OWN can:

- POST `/privacy/exports` with `{publicKey: "-----BEGIN PUBLIC KEY-----..."}` to queue a JSON export. RSA public keys must be 2048–8192 bits. Keep the private key on the client; the server never receives or stores it.
- GET `/privacy/requests/:id` to read their own request status and, when complete, a signed download link. Other users receive 404. Responses prohibit caching. The link expires no later than 24 hours after the original request, even if polled again; completion does not restart its lifetime.
- POST `/privacy/erasure` with `{confirmation: "DELETE MY ACCOUNT"}` to request irreversible account erasure. Once complete, existing JWTs are refused through REST and socket authentication. Completion can no longer be polled with the erased account's token; operators can inspect the job status.

The envelope contains base64 `wrappedKey`, `iv`, `tag`, `aad`, and `ciphertext`, plus version/cipher identifiers. Unwrap the 32-byte AES key using the recipient RSA private key with OAEP/SHA-256; decrypt using AES-256-GCM, the supplied IV, AAD and tag. Authentication failure means the archive is invalid. Fresh keys/IVs are generated for every export/retry, and the temporary plaintext Buffer/key are cleared after encryption. JavaScript cannot guarantee removal of prior string copies from garbage-collected memory.

The JSON manifest classifies every Prisma table and includes scalar, owner-filtered records plus owned squad descendants, financial evidence, chat and security records. It excludes credential secrets and other users' identities/private review payloads; sensitive joint evidence is intentionally redacted. Special policies restrict shared payout arrays and contract event payloads. SQL-owned user tables are explicitly classified; unknown new user-data tables fail the export until given a policy. Counts above 50,000 rows per table or 50 MB require operator-assisted export rather than silently truncating data. Process-local telemetry/session inventories cover the current instance; deploy centralized retention/export adapters if complete cross-instance operational logs are required.

Erasure deletes personal and authentication records, chat, own private security data, old encrypted cloud archives and shared login challenges/baselines. It replaces email/username/name and removes password/Google credentials, wallet associations, profile and referral attributes. Necessary transaction/audit and historical game relationships remain pseudonymously linked to a tombstone; public blockchain records cannot be erased. Immutable financial evidence is retained rather than rewritten. The manifest documents omitted secrets and shared security payloads. Operators must define lawful retention and backup deletion policies separately; this feature is not a claim of universal legal compliance or cryptographic erasure of unencrypted historical database backups.

Checks: `npm ci`, `npm run build`, `npm test` in backend. Pure tests verify recipient-only decryption, tamper rejection, manifest scoping and retained financial history. The actual PostgreSQL integration test requires a disposable localhost `fantasy_454` database with schema/migration and matching DATABASE_URL/FANTASY_TEST_DATABASE_URL; it uses an in-memory cloud-storage adapter, creates synthetic accounts and verifies archive extraction, expiry, owner isolation and cascading erasure. It intentionally retains synthetic pseudonymous financial records as production would; do not target a live database.
