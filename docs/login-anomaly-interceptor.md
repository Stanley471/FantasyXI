# Login anomaly interceptor (#453)

Deploy `20261119190000_login_security_activity` using the normal Prisma migrations, regenerate the client and run the backend build. The production login service holds sign-ins requiring more than 800 km/h, an observed ASN shift, or an IP listed by the configured threat feed. Held password/Google sign-ins receive an expiring email challenge and no access/refresh token. Existing enrolled passkeys already require a verified WebAuthn assertion; successful assertions update the verified-location history.

Production requires Redis with EVAL/atomic Lua and KEEPTTL support (Redis 6+), and a working existing email provider (`RESEND_API_KEY` or configured SendGrid provider, plus `EMAIL_FROM`). Missing shared state or failed challenge delivery fails closed. Challenge attempt counting and successful single-use consumption are atomic across processes. Codes are hashed in shared storage and never returned in responses. Local in-memory behavior is for development/injected tests only.

Set `LOGIN_TRUSTED_PROXY_CIDRS` to the actual origin-facing proxy addresses/subnets, `GEOIP_HEADER_SOURCE` to `cloudflare` or `cloudfront`, and optionally `LOGIN_ASN_HEADER` to the proxy-provided ASN header. Configure Express's trusted proxy policy consistently, restrict direct origin access, and have the trusted proxy overwrite incoming forwarded IP/location/ASN headers. Untrusted socket peers cannot supply geographic or ASN evidence; configured-but-unavailable location evidence refuses authentication. An unconfigured location provider cannot detect geographic travel. Coordinates come from IP estimates and are stored rounded to two decimals; they are not GPS evidence.

`LOGIN_THREAT_FEED_URL` is an operator-selected HTTPS endpoint returning a JSON array of individual IPv4/IPv6 strings (Tor/proxy/known-malicious exit nodes). The feed is refreshed on login after 15 minutes, limited to 2 MB/100,000 IPs and fetched with a 5-second timeout and no redirects. Refresh failures may use the last good list for up to one hour, then fail closed. With no feed configured, IP-list risk detection is disabled. Select and maintain a trusted feed operationally; tests never contact a live intelligence provider.

The existing password login/challenge API retains its EMAIL_OTP contract. POST `/auth/login/verify` verifies the challenge, and GET `/auth/security-activity` exposes only the authenticated account's last 100 activity rows: device/browser, IP, approximate location, ASN, outcome and timestamp. Successful challenge verification records the trusted location. A remembered device does not bypass ASN, feed or travel checks.

Google callback API clients requesting JSON receive HTTP 202 with the same challenge metadata when held. Browser redirects carry `challengeId`, `method` and `expiresAt` in the `/auth/callback` fragment, without a JWT. Frontend consumers must render the existing email verification flow for that fragment and submit the challenge through the API before treating the user as authenticated. This backend change does not add a new frontend screen. Internal AuthService callers that omit request context preserve the legacy non-request behavior; every HTTP sign-in controller supplies trusted request context.

Run `npm ci`, `npm run build`, `npm test` in backend. Unit tests cover geographic boundaries/timing, concurrent replay, ASN/feed changes, forged proxy evidence and stale feeds. To run the actual PostgreSQL integration case, use a disposable localhost `fantasy_453` database with the schema/migration and matching DATABASE_URL/FANTASY_TEST_DATABASE_URL. It verifies real password and Google holds, token withholding, email-code completion and persisted own-user history/trusted locations. Mail and network dependencies are injected; no real messages are sent.
